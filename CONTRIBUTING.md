# Contributing to Taarib

There are two kinds of contribution and they take different routes. Translations go through
the application; code goes through pull requests. Both end at the same place: one person reads
them.

Arabic follows the English, at [المساهمة في تعريب](#المساهمة-في-تعريب). The translation half
is a full parallel text — most translators read Arabic, and a contribution guide they cannot
read is not a contribution guide. The code half is condensed there and full here, because the
details it carries are file paths, command lines and compiler messages that appear in one
language only.

---

## Contributing a translation

### You do this inside Taarib, not on GitHub

Open the game in Taarib, extract its strings, translate them in the workspace, compile, and
press submit. The application does the rest: it seals the package with your contributor key,
builds the registry record, forks the registry repository, stages the package, pushes a branch,
and opens a pull request. Those six steps are named individually in the progress report, so a
failure tells you which one failed rather than "submission failed".

You never write registry JSON by hand, and a pull request that edits the registry by hand will
be closed with a pointer back here. The format is machine-written on purpose: a hand-edited
record is a record nobody verified.

### The submit button is inactive until the checks pass

Five checks block submission. They are not advisory and there is no override.

| Check | What it means |
| --- | --- |
| The hard checks | The compiler's own refusals — the ones a package cannot be produced past at all. |
| The asset gate certificate | Proof that every byte in the package was generated by Taarib. Verified, never recomputed at this stage. |
| Coverage | At least **60%** of strings translated overall, and at least **85%** of what a player meets in the first hour of play. |
| Duplicate of a published patch | You already have a published patch for this same build. Revise that one instead of publishing a second. |
| Import mappings | Every string you imported from an external source has a decision recorded against it. |

Four further conditions warn instead of blocking, and the gate will not mint a submission until
each one you triggered has been acknowledged:

- More than twenty strings overrun the space they have badly enough to need a rewrite.
- A quarter or more of the game is still in its original language.
- You have declared the translation method as machine translation with no human review. This is
  allowed. It is disclosed to every user who installs it.
- Your terminology disagrees with the project glossary.

The coverage floors exist because a patch that covers a third of a game is worse than no patch:
the player meets Arabic, trusts it, and then hits English in the middle of a sentence. The
first-hour floor is higher than the overall floor for the same reason — the opening hour is
where a player decides whether the patch works.

### What makes a translation good here

- **Translate the meaning, not the words.** A UI string with no room is a different problem
  from a line of dialogue.
- **Watch the preview.** Every line is rendered through the same text engine the game will use,
  at the real size, inside the real bounds. If it overflows there, it overflows in the game.
- **Leave placeholders alone.** `{0}`, `%s`, `[interact]`, `<b>` and every other dialect the
  extractor recognised are atoms. Taarib protects them across the machine-translation round
  trip and verifies that each one came back exactly once, at its span — but if you edit one by
  hand into something else, it will be reported and the submission will not pass.
- **Use the glossary.** A term that means one thing on the inventory screen and another in a
  quest log is a bug, and terminology drift is the most common reason a submission comes back
  for changes.
- **Diacritics are a decision, not a default.** Vocalising dialogue and stripping menus is a
  legitimate choice — it is the choice publishers make. It is recorded per patch rather than
  imposed.
- **Digits are a decision too.** Arabic-Indic `٤ ٥ ٦` and Eastern Arabic-Indic `۴ ۵ ۶` are
  different codepoints, not different renderings of the same ones. A Persian patch that leaves
  `٤` in its text shows a Persian reader an Arabic four. Taarib records the digit policy in the
  patch; pick it deliberately.

### The review model, and the fact that one person signs everything

A submission lands in the project owner's review queue. It goes nowhere public until it leaves
that queue.

Review means it is read string by string, previewed through the real text engine at real size
inside real interface bounds, and optionally installed into a sandboxed copy of the game. Five
actions are possible and all of them are logged: comment, request changes, reject with a
written reason, approve, or — for something already published — withdraw.

A rejection reason cannot be blank. Neither can a withdrawal reason: a patch vanishing from
someone's library with no explanation is not an acceptable outcome, and the code refuses to
construct one.

**There is no automatic publishing path.** Not for clean automated checks, not for trusted
contributors, and not for the owner's own translations, which go through the same submission
object so that provenance and signature are uniform across the whole catalogue. Every published
patch is signed with the owner's Ed25519 key at the moment of approval, and clients refuse
anything unsigned, mismatched, or revoked.

This is not a governance preference. The product asks users to let it modify files inside games
they paid for, and a single reviewed signing chokepoint is the only structure in which the
promise *"if Taarib installed it, a person approved it"* stays true. Review authority is
possession of the signing key, not a row in a permissions table — every review entry point
requires a token that can only be minted by proving possession of that key, so the console is
not merely hidden from a contributor's session; the argument it needs cannot be produced there.

The practical consequence for you: review is as fast as one person, and it will sometimes be
slow. Requesting changes is the normal outcome, not a rebuke.

## Contributing code

### Read the roadmap first

[`ROADMAP.md`](ROADMAP.md) is the contract for the whole product — twenty-four phases, each
with its scope, its constraints, its dependencies and its definition of done. It is a
specification, not a summary.

Section 2 holds eight settled architectural decisions. **A change that contradicts one of them
will be declined regardless of how well it is written.** The one most often reopened by
newcomers is Decision 1 — never produce Unicode presentation forms — and
[`docs/taqdimiya.md`](docs/taqdimiya.md) exists so that the argument does not have to be had
from scratch each time. Read it before proposing anything that touches shaping, the atlas, or
an adapter's draw path.

### The toolchain is pinned, and mixing toolchains breaks the workspace

[`rust-toolchain.toml`](rust-toolchain.toml) pins **1.95.0**. That is not caution: it is the
highest MSRV in the resolved dependency graph. Edition 2024 only needs 1.85, so the binding
constraint is a dependency, not the edition.

rustup honours the pin automatically inside the workspace, so `cargo build` here is already
1.95.0 and you will normally never think about it. The trap is one step outside.

**Do not build a scratch crate that path-depends on Taarib into the same target directory
without pinning the toolchain.** A throwaway harness in `/tmp` with a `Cargo.toml` of its own
is outside the workspace, so the toolchain file does not reach it; plain `cargo` there uses your
rustup default. If that default is not 1.95.0, it recompiles the shared dependencies with a
different compiler into the shared target directory, and the next build inside the workspace
fails like this:

```
error[E0514]: found crate `taarib_jisr` compiled by an incompatible version of rustc
```

Nothing in the workspace changed. The artefacts did.

Two habits avoid it entirely: write `cargo +1.95.0` in any scratch harness, and give the
harness its own `--target-dir` inside its own directory.

**When it happens anyway, the repair is targeted:**

```bash
cargo clean -p taarib-jisr   # the crate the error names, not the whole tree
```

Not `cargo clean`. A full clean throws away an hour of compilation to fix something that takes
seconds, and this workspace is large enough that the difference is felt every time.

### What has to pass

```bash
cargo check --workspace --all-targets
cargo clippy --workspace --all-targets
cargo test --workspace
cargo deny check
```

and, from `apps/studio`:

```bash
npx tsc -p tsconfig.json
npx tsc -p tsconfig.node.json
npx vite build
```

CI runs exactly these, on the same pinned toolchain. If they are green on your machine they are
green there.

Notes on each, because two of them surprise people:

- **`cargo check` before clippy, as its own step.** Clippy reports the same compile errors, but
  "your code does not build" and "your code builds and trips a lint" are different messages,
  and the first one should arrive first and fastest.
- **`--all-targets` is not optional.** It is what makes clippy look at test code, and test code
  is exactly where a stray `unwrap()` gets written. See the next section.
- **`cargo deny check` is not licence bookkeeping.** Two copies of `read-fonts` in the graph is
  a build failure, and a native HarfBuzz or `rustybuzz` entering the graph is a build failure,
  because the guarantee that the shaper's glyph identifiers are the rasterizer's glyph
  identifiers is only true while that holds. Policy lives in [`deny.toml`](deny.toml); changes
  to policy belong there and want an argument in the pull request.
- **Two `tsc` invocations, not one.** `npx tsc --noEmit` on its own would check `tsconfig.json`,
  which covers `src` under the DOM lib, and would silently skip `vite.config.ts`, which
  `tsconfig.node.json` covers under the Node lib. Both configs already set `noEmit`, so neither
  needs the flag. This matches what `pnpm build` does.
- **`vite build` after them.** `apps/studio/src-tauri` cannot compile until the frontend exists:
  `tauri.conf.json` points `frontendDist` at `../dist`, and `tauri-codegen` fails outright if
  that directory is missing. `dist/` is build output and is not committed, so a fresh checkout
  does not have it. Creating an empty `dist/` makes the Rust side compile and embeds an
  application with no interface in it, which is the worst kind of green there is.

### `cargo fmt --check` is red, tree-wide, and is not a gate

Stated here rather than left for you to discover at three in the morning.

`cargo fmt --all --check` currently reports about **5,400 hunks across 300 files**. The tree is
hand-formatted at 100 columns and rustfmt disagrees with a lot of it: compact struct literals
and `let … else` bodies it wants exploded across several lines, and
`match_block_trailing_comma` applied by hand in some files and not others.

None of that is a defect and none of it is your fault. Failing pull requests on it would teach
everyone to ignore a red check, which is worse than having no check. So CI runs the job with
`continue-on-error` — it is advisory, it is visible in every run, and it is not a gate.

What this means for you:

- **Do not run `cargo fmt` over the workspace.** You would produce a 300-file diff with your
  actual change buried somewhere inside it, and it would not be reviewable.
- **Do not reformat files your change does not otherwise touch.**
- Write new code to the settings in [`rustfmt.toml`](rustfmt.toml) — 100 columns, four spaces,
  Unix newlines, trailing comma on match blocks — and leave the rest alone.

The tree-wide reformat is pending. When it lands, this section and the `continue-on-error` in
CI go away together.

### The lint wall

The workspace denies far more than a Rust project usually does, in
[`Cargo.toml`](Cargo.toml)'s `[workspace.lints]`. That file is the single source of lint truth;
CI deliberately does not add `-D warnings` on top of it, because a second and stricter policy
living in a file nobody reads while editing Rust is how a lint config drifts out of trust.

Denied by the compiler: `missing_docs`, `missing_debug_implementations`,
`unsafe_op_in_unsafe_fn`, `unreachable_pub`, and `rust_2018_idioms`.

Denied by clippy: `unwrap_used`, `expect_used`, `panic`, `todo`, `unimplemented`, `unreachable`,
`indexing_slicing`, `integer_division`, `float_cmp`, `mem_forget`, `exit`, `dbg_macro`,
`print_stdout`, `print_stderr`, `undocumented_unsafe_blocks`, `missing_safety_doc`,
`missing_panics_doc`, `missing_errors_doc`, `allow_attributes_without_reason`, and the
truncating, wrapping and sign-losing casts.

Warned: all of `pedantic` and `nursery`. Six of their lints are switched off — five with a
written reason beside them (`module_name_repetitions` because domain names repeat by design,
`similar_names` because transliterated Arabic names are legitimately similar, and three more),
and `significant_drop_tightening` with no reason at all, which is a gap someone should close.

[`clippy.toml`](clippy.toml) adds three bans worth knowing before you trip them:

- `std::env::var`, `var_os` and `vars` — configuration is resolved once by `taarib_usus::idadat`
  and is not read ad hoc. All three forms are named on purpose; a rule naming only `var` would
  be satisfied by writing `var_os`.
- `std::process::exit` — return a `Khata`; the process exits in one place.
- `std::sync::Mutex` and `RwLock` — use `parking_lot`'s, which do not poison and therefore do
  not need an unwrap at every lock.

#### This bites test code, and that is the part that catches people

`cargo test --workspace` will happily run a test full of `unwrap()`. `cargo clippy --workspace
--all-targets` will then refuse the same file, because `--all-targets` includes tests, examples
and benches, and the denied lints apply there identically.

So the failure mode is: your tests pass, you open a pull request, and CI fails on a lint in a
file `cargo test` was perfectly happy with. It has already caught people working on this
codebase.

The fix is not to write awkward tests. A test reports failure by panicking; a test that cannot
panic cannot fail. Every integration test file in the tree carries a file-level `allow` with a
`reason`, and `allow_attributes_without_reason` is denied, so the reason is mandatory rather
than decorative. Copy this shape:

```rust
//! What this file proves, in one sentence.

#![allow(
    clippy::panic,
    clippy::unwrap_used,
    clippy::expect_used,
    clippy::missing_panics_doc,
    reason = "a test reports failure by panicking; the lints are written for library code, \
              and honouring them here would mean a test that cannot fail"
)]
```

Take only the lints you actually need. A file that asserts and nothing else needs
`clippy::panic` alone — that is what most of the tree's test files carry. `indexing_slicing` is
a reasonable addition in a test that indexes a fixture at a known offset; it is not a reasonable
blanket.

Inline `#[cfg(test)] mod ikhtibarat` blocks live inside a library file, so a file-level `allow`
there would also relax the library code above it. Put the attribute on the test module instead:

```rust
#[cfg(test)]
#[expect(
    clippy::unwrap_used,
    reason = "fixtures are known-good; an unwrap here fails the test, which is the point"
)]
mod ikhtibarat {
```

Prefer `#[expect]` to `#[allow]` where the lint definitely fires — it tells you when the reason
stops being true. Use `#[allow]` where it might not fire, since an unfulfilled `#[expect]` is
itself a warning.

### The naming law

This is the project's most distinctive property and the one that confuses newcomers most, so it
gets a full section rather than a line.

**Identifiers are transliterated Arabic.** The registry client is `mustawda`, not `registry`.
Signature verification is `tahaqquq`, not `verify`. The signing crate is `khatm`, not `signing`.
Readiness is `jahiziya`, not `readiness`. There is no `utils`, no `helpers`, no `common`, no
`manager`, no `service`, no `handler` and no `engine` anywhere in the tree, and a pull request
that adds one will be asked to rename it.

#### Why

Because the domain is Arabic, and a name is the only part of a program that has to survive
being read by someone who did not write it.

This product is about the Arabic language: its script, its joining behaviour, its diacritics,
its numerals, its direction. The people who will maintain the parts that matter most — the
shaper, the glossary, the review queue — think about those things in Arabic. A codebase that
made them translate their own vocabulary into English at every function boundary would be
adding a layer of loss between the domain and the code, in the one project where that loss is
least affordable.

There is a second, more practical reason: the names are unique. `taarib_aman::tahaqquq` means
one thing in this codebase and grepping it finds every use. `verify` would collide with the
verb in a hundred dependencies and with three unrelated concepts in this tree alone.

#### How to name a new one

1. **Name the concept, in Arabic, as the domain names it.** Not a translation of the English
   word you started from — the Arabic term a person working in this domain would use. `khatm`
   (ختم) is *sealing*, which is what signing a package is; it is not a transliteration of
   "sign".
2. **Transliterate it in Latin letters, without diacritics and without digits.** Doubled
   consonants stay doubled (`tahaqquq`, `muharrik`). Prefer the spelling a reader would guess,
   not a strict scholarly scheme — the tree uses `jahiziya`, not `ǧāhizīya`.
3. **Check it does not already exist with another meaning.** Grep before you commit. The
   vocabulary is small and it collides.
4. **Add it to the lexicon** in `ROADMAP.md` section 4.1, which is canonical.

Types and functions take the domain concept as their name: Arabic transliteration where the
concept is specifically Arabic-typographic (`Tashkeel`, `Wasl`, `Rasm`, `Kashida`, `Ruqaa`,
`Basma`), and domain English where it is not. User-visible text is Arabic first, English second,
and never transliteration — a user is never shown the word `jahiziya`.

#### One live hazard: spell mirrored types identically

There is a real mismatch in the tree right now. Do not copy it.

The Rust enum is `JahiziyatTashghil`, in
`crates/taarib-mustalahat/src/muharrik.rs`. The hand-written TypeScript union that mirrors it,
in `apps/studio/src/maktaba/jahiziya.ts`, is spelled **`JahiziyaTashghil`** — one `t` short.

Both compile. Neither is wrong at runtime, because the wire format is the snake_case string
(`mukammala`, `naqisa`, `ghaiba`) and the names never meet. The cost is entirely in searching:
grep for one and you silently miss every use of the other, which is exactly the failure a
consistent vocabulary is supposed to prevent. The TypeScript file's own comment refers to "the
backend's `JahiziyatTashghil`", two lines above declaring it with the other spelling.

The rule: **a hand-written mirror of a generated type is spelled identically to it.** The
Arabic word `جاهزية` transliterates naturally either way, which is exactly why it needs a rule
rather than an instinct. Most of the command surface is generated into
`apps/studio/src/mustalahat/awamir.ts` by `tauri-specta` and cannot drift; the hand-written
helpers around it can, and this is what that looks like.

### Comments and documentation

**Comments say WHY, not WHAT.** The code already says what it does. A comment that restates it
is noise that goes stale. A comment that records why the obvious approach was rejected is the
most valuable line in the file. The tree is full of the second kind, and they are the reason a
stranger can change something here without breaking an invariant nobody wrote down.

The one that reads best as a model, from `Cargo.toml`, on `panic = "unwind"` in the release
profile:

> unwind, not abort: every library in this workspace can end up loaded inside somebody else's
> game process, where a panic must be caught at the ABI edge and reported. `panic = "abort"`
> would terminate the player's game instead.

**File headers are one sentence, then the reasoning.** Every module opens with a `//!` header
whose first line is a single sentence naming what the file is for — that line is what rustdoc
shows in an index, so it has to stand alone. Everything after it is prose about how and why.
Some headers in this tree run to eighty lines, and that is fine; what is not fine is a first
line that needs the second to make sense.

**Doc comments carry purpose, and the sections that apply.** `missing_docs` is denied, so every
public item has one. Beyond that:

- `# Errors` on anything returning `Result`, naming which variants and when. `missing_errors_doc`
  is denied; there are about 1,080 of these in the tree.
- `# Safety` on every `unsafe fn`, stating the contract the caller must uphold.
  `missing_safety_doc` is denied.
- `// SAFETY:` on every `unsafe` block, stating why the contract holds *here*.
  `undocumented_unsafe_blocks` is denied; there are about 670 of these.
- `# Panics` on the rare function that can panic. There are three in the tree, which is the
  intended number.

**If you change behaviour a header explains, change the header.** A doc comment describing code
that no longer exists is worse than no doc comment, because someone will trust it.

### Three crates are Windows-only in substance

`taarib-mudkhal` (the `version.dll` proxy), `taarib-tabaqa` (the D3D11, D3D12, OpenGL and
Vulkan presentation hooks) and `taarib-haqn` (process injection) carry their real content behind
`#[cfg(windows)]`.

All three **compile on Linux**, which is the problem. A Linux-only `cargo check --workspace`
reports green having compiled none of that code. Until 2026-09-04 the Windows halves of these
three crates had never been compiled at all.

If you touch any of them, check on Windows and say so in the pull request. CI treats Windows as
a first-class matrix leg for the same reason — a regression in those halves has to fail a pull
request, not a release.

### Adding support for a new game engine

This is the contribution the project wants most, so here is the honest shape of it.

**There is no engine registry.** Adding an engine means adding one variant to `AilatMuharrik`
in `crates/taarib-mustalahat/src/muharrik.rs` and then repairing roughly **eleven exhaustive
`match` arms** the compiler points you at, plus about **six lists it does not**. That is by
design, and `crates/taarib-istikhraj/src/tawjih.rs` says why, on `Mustakhrij::li_aila`:

> Total over `AilatMuharrik` on purpose: a new variant added to the vocabulary makes this
> function stop compiling, which is the point. A wildcard arm here would let a new engine
> silently fall into "no extractor" and ship that way.

Expect a day of following compiler errors, and expect the six silent ones to be the part that
bites.

Also worth knowing before you start: an unrecognised engine is not an unsupported game. Anything
Taarib cannot identify falls to tier 3, the translation overlay — the game is not modified and
Arabic is drawn over it. Adding an engine moves a game *up* from tier 3.

#### The route

1. **Vocabulary.** Add the `AilatMuharrik` variant; fix `AilatMuharrik::ism`. Add `ItarNusus`
   variants for the engine's text surfaces and fix `ItarNusus::wasf_arabi`. Add a
   `KhalfiyaBarmajiya` variant only if the scripting runtime is genuinely new. `Tabaqa`,
   `JahiziyatTashghil` and `JawdaMutawaqqaa` never gain variants — three tiers, three readiness
   answers and four quality levels are the product's whole vocabulary.
   `AilatMuharrik::qabil_lil_tarqee` uses `matches!` and will not break; check it by hand.

2. **Detection.** `crates/taarib-muharrik/src/dalail/` is organised by *evidence source*, not by
   engine — directory shape, binary signature, embedded metadata, container header — because an
   engine is identified by independent sources agreeing, and a tree organised by engine would
   push every detector towards answering on its own. Add signature rows to `DALALAT`, `RUMUZ`
   and `BASMAT` in `dalail/thunai.rs`, then either add a `HadafNusus` variant in `dalail/nusus.rs`
   (fixing its three matches and the array length in `jamee`) or write a new `dalail/<engine>.rs`
   implementing the `Fahis` trait and register it in `dalail::kul()`.

   A detector observes and never concludes: an unparseable file returns `HasilatFahs::la_shay()`,
   not an error. Evidence weight is 0 to 100 on a documented scale — a file only one engine ships
   is 90 or more, a shared file is 40 to 60, a merely suggestive name is under 30. The single
   place an opinion is formed is `tahdid::hall`.

3. **Resolution.** Three functions in `crates/taarib-muharrik/src/tahdid.rs`: `rutba` (the
   tie-break rank), `khalfiya_tunasib`, `khalfiya_bunyawiya`.

4. **Capability.** Four functions in `crates/taarib-muharrik/src/imkaniyat.rs`:
   `tabaqa_min_muharrik` (the tier plus the two user-facing sentences, Arabic and English),
   `jahiziya`, `hudud_aila`, `jawda_min_itarat`. Add a `naqs_<engine>()` helper beside the
   existing ones. A `Hadd` carries two complete sentences addressed to a player, not to a
   maintainer.

5. **Raise `ISDAR_FAHS`, in the same commit.** `crates/taarib-muharrik/src/imkaniyat.rs`. The
   rule is at the constant: raise it whenever a change would produce a different report for a
   game whose files did not change — a new detector, a corrected weight, a changed tier rule, a
   reworded limitation. Adding an engine always counts.

   This is worth understanding rather than obeying. Forgetting it passes your local testing,
   because your database is fresh. It passes review, because the diff looks complete. It then
   fails silently, forever, and only for users who already own the game — they keep the stale
   conclusion the old probe reached. `crates/taarib-muharrik/src/bitaqa.rs` spells the trap out
   in its header.

6. **Extraction.** `crates/taarib-istikhraj/src/tawjih.rs` — a `Mustakhrij` variant and arms in
   `li_aila`, `yastafeed_min_iltiqat` and `ism`, plus `istakhrij` in `nusus.rs`. Then a reader
   module, or an arm in `nusus::istakhrij` if it is a script engine. Every container reader is
   written in this repository; no third-party game-asset library is used anywhere in extraction.

7. **The write side.** There is **no shared patcher trait across the crates** — each has its own,
   and a pull request should not invent one as a side effect. The rule for where your code goes:

   - **A module in `taarib-muhawwil-nusus`** if the engine's content is plain data or interpreted
     script, so patching the files is more robust than injecting into the process. The game then
     loads Taarib's translations through its own loader, on every version, with no hook to break
     when the engine updates. That crate deliberately does not depend on `taarib-jisr`, because
     it never crosses the ABI.
   - **Its own crate** if the engine needs a native in-process payload — a loader, hooks, vtable
     work, container readers at the scale of `taarib-muhawwil-godot` or `taarib-muhawwil-unreal`.
     Needing the ABI at runtime is the tell.

   In `taarib-muhawwil-nusus`, route every file touch through `&mut dyn Hafiz`; the reviewer's
   check is that `fs::File::create` outside `hifz` returns the `.rpa` builder and nothing else.

8. **Install.** `crates/taarib-tathbeet/src/tarkib.rs` — `hajat_itar` and `mulhaqat_muharrik`
   are exhaustive; `hajat_maa_tabaqa` has a wildcard and needs checking by hand.

9. **The in-game adapter.** `adapters-script/<engine>/`, or a C# project like `unity/`. The
   contract, from `adapters-script/README.md`, is absolute: *no file in that tree shapes Arabic,
   reorders a bidirectional line, chooses a kashida, positions a diacritic, or maps a codepoint
   to a glyph.* Adapters are transport and integration only. If a task seems to need text logic
   on that side of the boundary, the task is wrong or the ABI is missing something — extend
   `taarib-jisr` under its versioning rules, never the adapter.

   Two routes to the core: the C ABI in `crates/taarib-jisr` for native hosts (`ctypes` from
   Python, `Win32API` from Ruby, P/Invoke from C#), documented in `docs/abi.md`; or
   `crates/taarib-wasm` for JavaScript hosts, which exposes the same shape. A binding compares
   the **major** ABI version only, refuses a mismatch with a sentence naming both versions in
   the host's own log, and never gates on the minor.

   Target the interpreter the game ships, not the one you have: Python 3.9 for Ren'Py 8, Ruby
   1.9.2 for RGSS3, ES5-compatible output for RPG Maker MV's NW.js.

10. **The lists nothing will tell you about.** `KUL_AILAT: [AilatMuharrik; 10]` in
    `crates/taarib-tilqai/src/fahs.rs` — bump the length or the gate test walks nine of ten
    engines. Also `ism_injilizi` and `istakhrij`/`yuqra` in `crates/taarib-tilqai/`,
    `yuqra_sakinan` in `apps/studio/src-tauri/src/tilqai_awamir.rs`, `ism_aila` in
    `crates/taarib-tilqai/src/bina.rs`, and `MUHARRIKAT` in
    `apps/studio/src/maktaba/hifz_khiyarat.ts`.

11. **Regenerate what is generated.** `schemas/*.json` with
    `cargo run -p taarib-mustalahat --features mukhattatat --bin mukhattatat`; the TypeScript
    command surface by running a debug build. Never hand-edit either.

12. **Documentation.** A row in [`docs/tashghil.md`](docs/tashghil.md), and this is the
    strictest evidentiary standard in the repository. Every row there was established by
    *reading* the adapter, not by running it; where it says a function has no caller, that is a
    grep over `crates/`, `apps/`, `unity/` and `adapters-script/`, not an impression. The fourth
    column is a function name and a `path:line`. The file's own warning:

    > A row that says a chain stops somewhere it no longer stops is worse than no row: it is a
    > claim with a file and a line number attached, which is exactly the shape of a thing people
    > stop checking.

    Then `docs/bidaya.md` §6 if the engine gets a native payload — the two files must agree —
    and the crate table in `docs/mimar.md` if you added a crate.

13. **Tests and fixtures.** There are three tiers of evidence and the test's own header must say
    which one it used:

    - **Produced by the real engine.** `crates/taarib-muhawwil-godot/tests/thalith.rs` — every
      fixture came out of Godot 3.6.stable running headless, with a table saying how each was
      produced. This is the standard to aim at.
    - **Read out of shipped games and pinned as constants.**
      `crates/taarib-muhawwil-unreal/tests/basmat.rs` — 114,918 hashes reproduced across four
      named Steam titles, with the date and library path recorded.
    - **Authored, and labelled as authored.**
      `crates/taarib-muhawwil-nusus/tests/dawrat_kitaba.rs` says so under its own heading: no
      game of those engines is installed on the machine it was written on, so every fixture is
      constructed from the format definitions — *a weaker proof than a shipped game and a much
      stronger one than a mock, because the bytes are produced independently of the code under
      test and are rejected by it if they are wrong.*

    The write-side test shape is read → translate → write → **read back with this crate's own
    reader**, comparing Arabic byte for byte, because a container holding the right bytes at the
    wrong offset is a container the game will not load and only the reader can tell the two
    apart. Two assertions are worth copying verbatim: no Arabic Presentation Forms anywhere in
    any output (`U+FB50`–`U+FDFF`, `U+FE70`–`U+FEFF`), and every user-facing sentence present in
    both Arabic and English — a row with an empty sentence is a screen with a blank on it.

If that list looks long, it is, and shortening it would mean a wildcard arm somewhere that lets
an engine ship half-supported. If you are going to attempt one, open an issue first with the
*Support for a new engine* form: what the engine keeps its text in, and how it can be identified
on disk, are the two answers that decide whether the rest is a week or a month.

## Reporting a bug

[GitHub Issues](https://github.com/cc1a2b/taarib/issues), through one of the forms. They ask for
specific things — the launcher, the detected engine, the build's trust anchor, the compatibility
report — because a report without those cannot be diagnosed, and asking for them one at a time
costs you more than filling them in once.

The two collected from inside the application are worth knowing about before you need them.
**Diagnostics → Compatibility report** writes one JSON file holding the detected engine and its
evidence, the tier, the readiness answer, the named limitations and the recorded build
identifier. **Diagnostics → Build the bundle** collects the logs, the settings tree, a statement
of this machine and build, and every compatibility report so far, into one plain uncompressed
folder you can read before you share it. Nothing from the keychain is in either.

Error messages carry a code (`TAARIB-E-####`) allocated from a per-area block, so the code alone
narrows the search to one crate. They are written to be pasted.

**Security issues do not go here.** See [`SECURITY.md`](SECURITY.md) — this project modifies
game installs, verifies signatures against a key compiled into the binary, and loads code into
processes it does not own, so the boundary matters.

Everyone taking part is expected to behave according to
[`CODE_OF_CONDUCT.md`](CODE_OF_CONDUCT.md).

# المساهمة في تعريب

للمساهمة نوعان ولكلٍّ مسار: الترجمات تمرّ عبر التطبيق، والشيفرة عبر طلبات السحب. وكلاهما ينتهي
إلى الموضع نفسه: شخصٌ واحد يقرؤها.

وقسم الترجمة هنا نصٌّ موازٍ كامل للإنجليزي. أمّا قسم الشيفرة فمختصَر، والإنجليزي أوفى منه، لأنّ
تفاصيله مساراتُ ملفّات وأوامر سطرٍ ورسائل مُصنِّف لا ترد إلا بلغةٍ واحدة.

## المساهمة بترجمة

### هذا يجري داخل تعريب لا على GitHub

افتح اللعبة في تعريب، واستخرج نصوصها، وترجمها في الورشة، ثم جمّع واضغط «تقديم». والتطبيق يتولّى
الباقي: يختم الحزمة بمفتاحك، ويبني سجلّ الفهرس، ويستنسخ مستودع السجلّ، ويجهّز الحزمة، ويدفع
فرعًا، ويفتح طلب دمج. وهذه الخطوات الستّ مسمّاة منفردةً في تقرير التقدّم، فيخبرك الفشل بأيّها فشل
بدل «فشل التقديم».

ولن تكتب JSON الفهرس بيدك أبدًا، وطلب السحب الذي يعدّل الفهرس يدويًّا يُغلَق مع إحالة إلى هنا.
والصيغة تُكتَب آليًّا عن قصد: السجلّ المحرَّر يدويًّا سجلٌّ لم يتحقّق منه أحد.

### زرّ التقديم معطَّل حتى تمرّ الفحوص

خمسة فحوص تمنع التقديم، وليست إرشادية، ولا تجاوز لها:

| الفحص | معناه |
| --- | --- |
| الفحوص الصارمة | رفوض المُجمِّع نفسه — التي لا تُنتَج حزمةٌ بعدها أصلًا. |
| شهادة بوّابة الأصول | إثبات أنّ كل بايت في الحزمة ولّده تعريب. يُتحقَّق منها ولا تُعاد حسابًا في هذه المرحلة. |
| التغطية | **60٪** من النصوص مترجَمة إجمالًا على الأقل، و**85٪** ممّا يلقاه اللاعب في الساعة الأولى. |
| تكرار رقعة منشورة | لك رقعة منشورة لهذا البناء نفسه. راجِع تلك بدل نشر ثانية. |
| ارتباطات الاستيراد | كل نصّ مستورَد من مصدر خارجي له قرار مسجَّل. |

وأربعة شروط أخرى تُحذِّر ولا تمنع، ولا تسكّ البوّابة تقديمًا حتى تُقِرّ بكلّ ما أثرتَه منها:
تجاوز أكثر من عشرين نصًّا لمساحتها تجاوزًا يستدعي إعادة الصياغة؛ وبقاء رُبع اللعبة فأكثر بلغتها
الأصلية؛ وإعلانك أنّ الطريقة ترجمة آلية بلا مراجعة بشرية — وهذا مسموح، ويُفصَح عنه لكل مَن
يثبّتها؛ ومصطلحاتٌ تخالف مسرد المشروع.

وحدود التغطية موجودة لأنّ رقعةً تغطّي ثلث اللعبة أسوأ من لا رقعة: يلقى اللاعب العربية فيثق بها،
ثم يصطدم بالإنجليزية في وسط جملة. وحدّ الساعة الأولى أعلى من الحدّ العام للسبب نفسه: الساعة
الأولى هي التي يحكم فيها اللاعب على الرقعة.

### ما الذي يجعل الترجمة جيّدة هنا

- **ترجم المعنى لا الألفاظ.** نصّ واجهة لا مساحة له مسألةٌ غير سطر حوار.
- **تابع المعاينة.** كل سطر يُرسَم بمحرّك النصّ نفسه الذي ستستعمله اللعبة، بالحجم الحقيقي، داخل
  الحدود الحقيقية. فإن تجاوز هناك، تجاوز في اللعبة.
- **لا تمسّ العناصر النائبة.** `{0}` و`%s` و`[interact]` و`<b>` وكل لهجةٍ أخرى عرفها المستخرِج
  ذرّاتٌ لا تُجزَّأ. يحميها تعريب عبر دورة الترجمة الآلية ويتحقّق من عودة كلٍّ منها مرّةً واحدة
  في موضعها بالضبط — لكنّك إن غيّرت واحدًا بيدك إلى غيره، أُبلِغ عنه ولم يمرّ التقديم.
- **استعمل المسرد.** المصطلح الذي يعني شيئًا في شاشة المخزون وآخر في سجلّ المهام خللٌ، وانحراف
  المصطلح أكثر أسباب إعادة التقديم للتعديل.
- **التشكيل قرار لا افتراض.** تشكيل الحوار وتجريد القوائم اختيارٌ مشروع، وهو ما يفعله الناشرون.
  ويُسجَّل لكل رقعة بدل فرضه.
- **الأرقام قرار كذلك.** `٤ ٥ ٦` العربية-الهندية و`۴ ۵ ۶` الشرقية نقاطُ ترميزٍ مختلفة لا رسمان
  لمجموعة واحدة. والرقعة الفارسية التي تترك `٤` تُري القارئ الفارسي أربعةً عربية. يسجّل تعريب
  سياسة الأرقام في الرقعة، فاخترها عن قصد.

### نموذج المراجعة، وأنّ شخصًا واحدًا يوقّع كلّ شيء

يصل التقديم إلى طابور مراجعة مالك المشروع، ولا يذهب إلى العلن حتى يغادر ذلك الطابور.

والمراجعة أن يُقرأ نصًّا نصًّا، ويُعايَن بمحرّك النصّ الحقيقي بالحجم الحقيقي داخل حدود الواجهة
الحقيقية، ويُثبَّت اختياريًّا في نسخة معزولة من اللعبة. وخمسة إجراءات ممكنة وكلّها مسجَّلة:
تعليق، وطلب تعديل، ورفضٌ بسبب مكتوب، واعتماد، وسحبٌ لما نُشِر.

وسبب الرفض لا يجوز أن يكون فارغًا، ولا سبب السحب: اختفاء رقعة من مكتبة أحدهم بلا تفسير نتيجةٌ
غير مقبولة، والشيفرة ترفض إنشاءها.

**لا مسار نشر تلقائي.** لا لفحوصٍ نظيفة، ولا لمساهمين موثوقين، ولا لترجمات المالك نفسه، فهي تمرّ
بكائن التقديم نفسه ليبقى الإسناد والتوقيع موحَّدين في الفهرس كلّه. وكل رقعة منشورة تُوقَّع بمفتاح
Ed25519 الخاصّ بالمالك لحظة الاعتماد، ويرفض العملاء كل غير موقَّع أو غير مطابق أو مسحوب.

وليست هذه تفضيلًا في الحوكمة. المنتج يطلب من المستخدمين أن يأذنوا له بتعديل ملفات داخل ألعاب
دفعوا ثمنها، ونقطة توقيعٍ واحدة مُراجَعة هي البنية الوحيدة التي يبقى فيها الوعد صادقًا: **إن
ثبّته تعريب فقد اعتمده إنسان**. وسلطة المراجعة حيازةُ مفتاح التوقيع لا صفٌّ في جدول صلاحيات:
فكلّ مدخلٍ إلى المراجعة يطلب رمزًا لا يُسكّ إلا بإثبات حيازة ذلك المفتاح.

والنتيجة العملية لك: المراجعة بسرعة شخصٍ واحد، وستكون بطيئة أحيانًا. وطلب التعديل هو المخرج
الطبيعي لا توبيخًا.

## المساهمة بالشيفرة

اقرأ [`ROADMAP.md`](ROADMAP.md) أوّلًا؛ فهو عقد المنتج كلّه: أربعة وعشرون طورًا، لكلٍّ نطاقه
وقيوده واعتمادياته وتعريف إتمامه. وهو مواصفة لا ملخّص. ويحمل قسمه الثاني ثمانية قرارات معمارية
مستقرّة، **والتغيير الذي يناقض واحدًا منها يُرفض مهما أُحسِنت كتابته**. وأكثرها إعادةً للفتح من
القادمين الجدد القرار الأول — ألّا تُنتَج أشكال يونيكود التقديمية — ووُجد
[`docs/taqdimiya.md`](docs/taqdimiya.md) حتى لا تُعاد الحجّة من الصفر كل مرّة.

### السلسلة مثبَّتة عند 1.95، وخلطُ السلاسل يكسر الشجرة

يثبّت [`rust-toolchain.toml`](rust-toolchain.toml) الإصدار **1.95.0**، وهو أعلى حدٍّ أدنى في
رسم الاعتماديات لا احتياطًا. ويحترمه rustup تلقائيًّا داخل الشجرة، والمصيدة خطوةٌ خارجها: مشروعٌ
مؤقّت في `/tmp` يعتمد على كريتات تعريب بمسار، ويُبنى بـ`cargo` مجرَّدًا، يستعمل سلسلتك
الافتراضية لا المثبَّتة، فيعيد تصريف الاعتماديات المشتركة في دليل الهدف نفسه، فيفشل البناء التالي
داخل الشجرة بـ:

```
error[E0514]: found crate `taarib_jisr` compiled by an incompatible version of rustc
```

والعادتان اللتان تمنعانه: `cargo +1.95.0` في كل مشروعٍ مؤقّت، و`--target-dir` خاصٌّ به داخل
دليله. وإن وقع رغم ذلك فالإصلاح **موضعي**: `cargo clean -p <الكريت الذي سمّاه الخطأ>`، لا
`cargo clean` كاملًا — فالتنظيف الكامل يُلقي بساعةٍ من التصريف لإصلاح ما يستغرق ثوانٍ.

### ما يجب أن يمرّ

```bash
cargo check --workspace --all-targets
cargo clippy --workspace --all-targets
cargo test --workspace
cargo deny check
```

ومن `apps/studio`:

```bash
npx tsc -p tsconfig.json
npx tsc -p tsconfig.node.json
npx vite build
```

واثنتان من هذه تفاجئان: `--all-targets` ليست خيارًا — بها يرى clippy شيفرةَ الاختبار، وهي بالضبط
موضع `unwrap()` الشارد. و`tsc` يُستدعى مرّتين لا مرّة: `tsconfig.json` يغطّي `src`،
و`tsconfig.node.json` يغطّي `vite.config.ts`، والاكتفاء بالأول يتخطّى الثاني صامتًا. وكلاهما
يضبط `noEmit` أصلًا. و`cargo deny check` ليس مسكَ دفاترِ تراخيص: نسختان من `read-fonts` في الرسم
فشلُ بناء، ودخول HarfBuzz أصليّ أو `rustybuzz` فشلُ بناء، لأنّ ضمان أنّ معرّفات المُشكِّل هي
معرّفات المُنقِّط لا يصحّ إلا ببقاء ذلك.

### `cargo fmt --check` أحمر في الشجرة كلّها، وليس بوّابة

يُقال هنا صراحةً بدل أن تكتشفه بنفسك: يبلّغ `cargo fmt --all --check` اليوم عن نحو **5,400 موضع
في 300 ملف**. الشجرة منسَّقة يدويًّا عند 100 عمود، و rustfmt يخالفها في كثير: بِنى ومتونُ
`let … else` مضغوطة يريد فردها، و`match_block_trailing_comma` طُبِّق في ملفّاتٍ دون أخرى. وليس
شيءٌ من ذلك عيبًا ولا ذنبَك، وإفشالُ طلبات السحب عليه يعلّم الجميع تجاهلَ فحصٍ أحمر، وهو أسوأ من
غيابه. فيجري في CI استرشاديًّا بـ`continue-on-error`.

ويعني هذا لك: **لا تُجرِ `cargo fmt` على الشجرة**، ولا تُعِد تنسيق ملفّاتٍ لم يمسّها تغييرك —
وإلا صار تغييرك الحقيقي مدفونًا في فرقٍ من ثلاثمئة ملف لا يُراجَع. واكتب الجديد وفق
[`rustfmt.toml`](rustfmt.toml). وإعادة التنسيق الشاملة مؤجَّلة، وحين تصل يزول هذا القسم
و`continue-on-error` معًا.

### جدار الفحوص، وأنّه يطال شيفرة الاختبار

يمنع `[workspace.lints]` في [`Cargo.toml`](Cargo.toml) من المُصنِّف: `missing_docs`
و`missing_debug_implementations` و`unsafe_op_in_unsafe_fn` و`unreachable_pub`. ومن clippy:
`unwrap_used` و`expect_used` و`panic` و`todo` و`unimplemented` و`unreachable`
و`indexing_slicing` و`integer_division` و`float_cmp` و`exit` و`print_stdout` و`print_stderr`
و`undocumented_unsafe_blocks` و`missing_safety_doc` و`missing_panics_doc` و`missing_errors_doc`
و`allow_attributes_without_reason` والتحويلات القاطعة. و`pedantic` و`nursery` تحذيرًا. ويمنع
[`clippy.toml`](clippy.toml) قراءة البيئة بصورها الثلاث، و`std::process::exit`، و`Mutex`
و`RwLock` من المكتبة القياسية.

**والمفاجأة أنّ هذا يطال الاختبارات.** فـ`cargo test --workspace` يمرّر اختبارًا مملوءًا
بـ`unwrap()`، ثم يرفض `cargo clippy --workspace --all-targets` الملفَّ نفسه. وقد أوقع هذا من عمل
على هذه الشيفرة فعلًا. والعلاج ليس اختباراتٍ ملتوية: فالاختبار يبلّغ عن فشله بالذعر، والذي لا
يذعر لا يفشل. فكل ملفّ اختبارٍ في الشجرة يحمل ترويسة إذنٍ **بسبب مكتوب** — و
`allow_attributes_without_reason` ممنوع فالسبب واجب لا زينة:

```rust
#![allow(
    clippy::panic,
    clippy::unwrap_used,
    reason = "a test reports failure by panicking; the lints are written for library code, \
              and honouring them here would mean a test that cannot fail"
)]
```

وخُذ ما تحتاجه فقط. أمّا وحدات `#[cfg(test)] mod ikhtibarat` داخل ملفّ مكتبة فضَع الإذن على
الوحدة نفسها لا على الملفّ، وإلا أرخيتَ القيد عن شيفرة المكتبة فوقها.

### قانون التسمية

المعرّفات عربيةٌ منقولة بحروف لاتينية: عميل الفهرس `mustawda` لا `registry`، والتحقّق من التوقيع
`tahaqquq` لا `verify`، وكريت التوقيع `khatm` لا `signing`، والجاهزية `jahiziya` لا `readiness`.
ولا `utils` ولا `helpers` ولا `common` ولا `manager` ولا `service` ولا `handler` ولا `engine` في
الشجرة كلّها.

**ولماذا؟** لأنّ المجال عربي، والاسم هو الجزء الوحيد من البرنامج الذي عليه أن ينجو من قراءة مَن
لم يكتبه. ومَن سيصون أهمّ الأجزاء — المُشكِّل، والمسرد، وطابور المراجعة — يفكّر فيها بالعربية،
وشيفرةٌ تُلزمهم بترجمة مفرداتهم عند كل حدّ دالّة تضيف طبقة فقدٍ بين المجال والشيفرة في المشروع
الذي هي فيه أغلى ما تُفقَد. ثمّ إنّ الأسماء بهذا فريدة: `tahaqquq` تعني شيئًا واحدًا هنا وتجدها
كلّها بالبحث، و`verify` تصطدم بمئة اعتمادية وبثلاثة معانٍ في هذه الشجرة وحدها.

**وكيف تسمّي جديدًا؟** سمِّ المفهوم بالعربية كما يسمّيه أهل المجال لا ترجمةً للكلمة الإنجليزية
التي بدأتَ منها — `ختم` هو ما تفعله بالحزمة، لا نقلٌ لحروف "sign". ثم انقله بحروفٍ لاتينية بلا
حركات ولا أرقام، والمشدَّد يبقى مضاعفًا (`tahaqquq`, `muharrik`)، بالرسم الذي يحدسه القارئ لا
بنظامٍ علمي صارم. ثم ابحث قبل أن تُثبِت؛ فالمفردات قليلة وتتصادم. ثم أضِفه إلى المسرد في القسم
4.1 من `ROADMAP.md` وهو المرجع.

**وفي الشجرة اليوم تعارضٌ حيّ لا تُقلِّده:** التعداد في Rust اسمه `JahiziyatTashghil`، ونظيرُه
المكتوب يدويًّا في TypeScript ضمن `apps/studio/src/maktaba/jahiziya.ts` اسمه `JahiziyaTashghil`
بتاءٍ ناقصة. وكلاهما يُصرَّف، ولا خطأ في التشغيل لأنّ صيغة السلك هي السلسلة
(`mukammala`/`naqisa`/`ghaiba`) ولا يلتقي الاسمان. والكلفة كلّها في البحث: تبحث عن أحدهما فتفوتك
كلّ مواضع الآخر — وهو بالضبط ما تُوجد المفردات الموحَّدة لمنعه. **والقاعدة: النظير المكتوب يدويًّا
لنوعٍ مولَّد يُهجّى مثله حرفًا بحرف.**

### التعليقات والتوثيق

**التعليق يقول لماذا لا ماذا.** الشيفرة تقول ماذا أصلًا، وتعليقٌ يعيدها ضجيجٌ يبلى، وتعليقٌ يسجّل
لماذا رُفض الحلّ البديهي أنفعُ سطرٍ في الملفّ. **وترويسة الملفّ سطرٌ واحد ثم التعليل**: أوّل سطرٍ
في `//!` جملةٌ تقوم بنفسها لأنّها ما يعرضه rustdoc في الفهرس، وما بعده نثرٌ في الكيف والعلّة.
**وتعليقات التوثيق تحمل الغرض وأقسامَه**: `# Errors` لكل ما يعيد `Result`، و`# Safety` لكل دالّة
`unsafe`، و`// SAFETY:` لكل كتلة `unsafe` تبيّن لماذا يصحّ العقد **هنا**، و`# Panics` للنادر الذي
قد يذعر. وإن غيّرت سلوكًا تشرحه ترويسة فغيّر الترويسة: توثيقٌ يصف شيفرةً لم تعد موجودة أسوأ من لا
توثيق، لأنّ أحدًا سيثق به.

### ثلاثة كريتات جوهرها لويندوز

`taarib-mudkhal` (وسيط `version.dll`) و`taarib-tabaqa` (خطّافات العرض لـD3D11 وD3D12 وOpenGL
وVulkan) و`taarib-haqn` (حقن العمليات) تحمل مضمونها الحقيقي خلف `#[cfg(windows)]`. **وثلاثتها
تُصرَّف على لينكس**، وهذه هي المشكلة: فحصٌ على لينكس وحده يخرج أخضر ولم يصرِّف شيئًا من تلك
الشيفرة. فإن مسستَ واحدًا منها ففافحص على ويندوز، وقُل ذلك في طلب السحب.

### إضافة دعم محرّك جديد

هذه أكثر مساهمةٍ يريدها المشروع، وشكلها الصادق: **لا سجلّ محرّكاتٍ يُضاف إليه صفّ**. إضافة محرّك
هي إضافة صنفٍ واحد إلى `AilatMuharrik` ثم إصلاح نحو **إحدى عشرة مطابقة شاملة** يدلّك عليها
المُصنِّف، ونحو **ستّ قوائم لا يدلّك عليها**. وهذا مقصود؛ يقول
`crates/taarib-istikhraj/src/tawjih.rs` عن `Mustakhrij::li_aila` إنّ الشمول متعمَّد: صنفٌ جديد
يوقف تصريف الدالّة، وهو المراد، وذراعٌ عامّة هنا كانت ستدع محرّكًا جديدًا يسقط صامتًا في «لا
مستخرِج» ويُشحَن كذلك.

والمسار كاملًا — بأسماء الملفّات والدوالّ — في القسم الإنجليزي أعلاه تحت *Adding support for a
new game engine*. وأهمّ ما فيه: **ارفع `ISDAR_FAHS` في الالتزام نفسه**؛ فنسيانه يمرّ في اختبارك
المحلّي (قاعدتك جديدة)، ويمرّ في المراجعة (الفرق يبدو تامًّا)، ثم يفشل صامتًا وإلى الأبد ولمن
يملكون اللعبة أصلًا وحدهم. وصفٌّ في [`docs/tashghil.md`](docs/tashghil.md) بأشدّ معيار بيّنةٍ في
المستودع: كلّ صفٍّ فيه أُثبِت بقراءة المحوّل لا بتشغيله، وعمودُه الرابع اسمُ دالّة و`path:line`.

وإن بدت القائمة طويلة فهي كذلك، واختصارها يعني ذراعًا عامّةً في موضعٍ ما تدع محرّكًا يُشحَن
نصفَ مدعوم. وإن عزمتَ عليها فافتح مسألةً أوّلًا بنموذج *Support for a new engine*.

### الالتزامات وطلبات السحب

صيغة Conventional Commits. وتغييرٌ منطقيّ واحد لكل طلب سحب. وإن مسّ التغيير طورًا في خريطة
الطريق فسمِّ الطور. وإن ناقض شيئًا مكتوبًا فقُل ذلك صراحةً وحاجِج فيه — فذلك نقاشٌ مرحَّب به،
واكتشافه في المراجعة ليس كذلك. والبناء في [`docs/bina.md`](docs/bina.md).

## الإبلاغ عن خلل

عبر [GitHub Issues](https://github.com/cc1a2b/taarib/issues) بأحد النماذج. وهي تطلب أشياء
بعينها — المشغّل، والمحرّك المكتشَف، ومرساة الثقة التي بُني عليها إصدارك، وتقرير التوافق — لأنّ
بلاغًا بلا هذه لا يُشخَّص، وسؤالك عنها واحدةً واحدة أكلفُ عليك من ملئها مرّة.

واثنان منها يُجمَعان من داخل التطبيق: **التشخيص ← تقرير التوافق** يكتب ملفّ JSON واحدًا يحمل
المحرّك المكتشَف وبيّناته، والطبقة، وجواب الجاهزية، والحدود المسمّاة، ومعرّف البناء المسجَّل.
و**التشخيص ← ابنِ الحزمة** يجمع السجلّات وشجرة الإعدادات وبيان هذا الجهاز والبناء وكلّ تقارير
التوافق في مجلّدٍ عاديّ غير مضغوط تقرؤه قبل أن تشاركه. ولا شيء من حافظة المفاتيح في أيٍّ منهما.

ورسائل الخطأ تحمل رمزًا (`TAARIB-E-####`) مخصَّصًا من كتلةٍ لكل مجال، فالرمز وحده يضيّق البحث
إلى كريتٍ واحد. وهي مكتوبةٌ لتُلصَق.

**والثغرات الأمنية لا تُبلَّغ هنا.** انظر [`SECURITY.md`](SECURITY.md).

ويُتوقَّع من كل مشارك الالتزام بـ[`CODE_OF_CONDUCT.md`](CODE_OF_CONDUCT.md).

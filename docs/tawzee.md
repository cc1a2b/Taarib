# التوزيع — the packaging and distribution contract

This file is the Phase 22 contract. Every packaging, staging, update and audit
task builds against the tables below and invents nothing. An artifact absent
from these tables does not ship; an artifact present here that cannot be staged
fails the staging step loudly, by name.

## 1. Signing identities

Two identities, structurally distinct in `taarib_khatm::malik`:

| identity | anchor | private-half custody | client behaviour |
| --- | --- | --- | --- |
| `tatwir` | `MIFTAH_TATWIR`, committed | a developer keychain; unprotected by design | badge shown in the studio footer; installs dev-signed packages |
| `isdar` | injected at build via `TAARIB_MIFTAH_ISDAR` (public half only, 64 hex) | generated inside the owner's passphrase-protected OS keychain, on the owner's machine; never a file, fixture, or environment variable | refuses `MIFTAH_TATWIR` signatures by name (`SababTawqee::TawqeeTatwir`) |

A release build with a malformed injected key, or one equal to the development
key, does not compile. Every shipped package below is built with the injection
present; a bundle whose `maalumat_taarib` reports `tatwir` is not a release.

**Recorded limitation (E/F/G payload bootstrap).** `taarib-mudkhal` opens each
payload beside it and calls `taarib_bidaya` when the payload exports it. Today
none of F1/G1/G2 exports that symbol: `taarib-tabaqa`, `taarib-muhawwil-unreal`
and `taarib-muhawwil-godot` expose library APIs that need a hooker, a
disclosure record or engine pointers to start, and the in-process bootstrap
that assembles those inside a game has not been built — it belongs to the same
gap as the empty `taarib-haqn` (a documented module header whose four modules
do not exist). Consequences, precisely: the overlay's **Vulkan layer** path
works today, because the Vulkan loader itself calls
`vkNegotiateLoaderLayerInterfaceVersion` in `taarib-tabaqa`; the D3D11/D3D12/GL
overlay paths and the Unreal and Godot takeovers load their module and then do
nothing. Staging them is still correct — they are the real artifacts, and the
symbol is what the bootstrap will export — but no packaging task may claim the
injection tier is live.

## 4. Staging

The staging tool is the binary crate `crates/taarib-tajmee`. It never builds
anything; it gathers already-built outputs into
`apps/studio/src-tauri/mawarid/`, verifies, and writes `bayan_mukawwinat.json`.
It exits non-zero listing **every** absent or hash-mismatched artifact, not the
first. `tauri.conf.json` declares `bundle.resources = ["mawarid"]`, so the
whole staged tree lands in the platform resource directory verbatim.

Fetched inputs (D1, J1) are pinned in `assets/aqfal/`: each lock entry is
`{ rabt, isdar, hajm, sha256 }`. The tool refuses an unlocked or mismatched
fetch; it never writes a hash it did not verify.

`bayan_mukawwinat.json`:

```json
{
  "mukhattat": 1,
  "isdar": "<workspace version>",
  "hadaf": "<target triple>",
  "milaffat": [ { "masar": "mukawwinat/…", "hajm": 0, "sha256": "…" } ]
}
```

Paths are forward-slash, relative to `mawarid/`. The manifest is written last;
its own absence marks a partial staging.

## 5. Runtime resolution

- `masarat::iktashif()` resolves the data root: `TAARIB_BAYANAT` override →
  portable marker → platform default. **Portable marker**: a file named
  `taarib.mahmul` beside the executable puts the data root at
  `<exe dir>/bayanat` and forbids every machine-global write (no keychain
  writes, no registry, no `~/.config`).
- On startup, `zamin_mukawwinat` (studio, `mukawwinat_tahmil.rs`) reads the
  bundled `bayan_mukawwinat.json` from the tauri resource directory, verifies
  it, and mirrors the tree into `masarat.mukawwinat()` — hash-compared, atomic
  per file, manifest written last. A missing or corrupt bundled artifact is a
  named startup diagnostic, never a crash and never a silent skip; installs
  that need the absent component refuse by name at `hamil_mukawwin`.
- Installs read components from `masarat.mukawwinat()` only. Nothing reads the
  resource directory at install time, so a running install survives an update
  swapping the bundle.

## 6. Self-update

New crate `crates/taarib-tahdith`. The channel manifest `tahdith.json` sits
under the official registry root (`masadir.rasmi`), signed detached
(Ed25519, `MudaqqiqEd25519`) by the identity the client trusts — a release
client refuses a dev-signed channel exactly as it refuses a dev-signed patch.
Per-target entries: `{ rabt, hajm, sha256, isdar, adna_isdar }`.

Swap rules: download to `masarat.sandooq()`, verify hash, then per format —
NSIS: run the verified installer silently on exit; AppImage: write beside the
current file, fsync, atomic rename, keep the previous as `*.sabiq` until one
clean launch; `.app`: staged directory swap by rename; `.deb`: check-only, the
package manager owns the swap. An interrupted update must leave the previous
version launchable; the data root, the component store and every installed
game are never touched by the updater.

## 7. Uninstall

The uninstaller (NSIS section; on Linux/macOS the same flow is reachable as
`taarib-studio --istiada`) first launches the Phase 20G library-wide restore —
every game with Taarib content installed is offered a full removal/restore —
and only then removes the application. The user's data root is left in place
unless they explicitly opt in to deleting it.
